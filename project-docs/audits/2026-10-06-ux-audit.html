Shoes On / pre-submission review

User experience audit

6 October 2026 | Focus: first setup, morning run, notifications, subscription, accessibility, and localization

Release read The core morning flow is clear and specific. Before a broad launch, resolve the trial reminder promise for people who deny notifications and confirm that localized App Store pages match the language available in the app. The run catch-up action also needs a recovery path.

Prioritized findings

P1 affects trust or access on a launch path and should be resolved for the affected audience. P2 is a meaningful recovery or accessibility gap to address before expanding reach.

P1, localized storefronts

Store copy is localized, core app copy appears English only

The repo contains store copy for 50 locales, while the app bundle has no .xcstrings, .strings, or .lproj resources. Visible onboarding, run, settings, notification, Watch, and purchase copy is written in English. A customer arriving from a translated product page can land in an English-only experience.

Recommendation

Localize the customer-facing app surfaces, including notification text and the Watch app, before enabling translated product pages. If launch is English only, keep App Store availability and listing languages aligned with that scope.

Evidence

ShoesOn/Info.plist:5 declares English as the development region. A repository search found no localization catalogs. The repo guide documents 50 store-copy locales.

P1, trial trust

The Day 5 reminder is promised even when notifications are denied

Onboarding requests notification access immediately before the Pro offer, but ignores the permission result and always shows “A reminder before your trial ends.” If the customer denies access, the reminder cannot reach them, yet the offer still presents it as part of the trial timeline.

Recommendation

Check notification authorization before showing the reminder promise. When access is off, say that the reminder requires notifications and provide a clear route to enable them, or make the reminder explicitly conditional.

Evidence

ShoesOn/Views/OnboardingView.swift:349-359 ignores the result. ShoesOn/Views/OnboardingView.swift:520-524 always shows the Day 5 reminder. Shared/Services/NotificationService.swift:50-60 schedules it after purchase.

P2, accessibility

Key text does not follow Dynamic Type, and onboarding progress is silent to VoiceOver

The custom onboarding title, reveal total, run step name and timer, paywall title, and summary headline use fixed point sizes. The visible page dots are hidden from accessibility and have no accessible page-count label. Large Text users may not get larger key content, and screen-reader users do not hear where they are in setup.

Recommendation

Use scalable text styles for custom headings and the timer while preserving the run layout. Announce the current setup page and total pages. Check the longest step name at the largest accessibility text size and with VoiceOver.

Evidence

ShoesOn/Views/OnboardingView.swift:163-168, 186-189, 265-269, 550-563; ShoesOn/Views/RunView.swift:158-182; ShoesOn/Views/PaywallView.swift:27-30.

P2, run recovery

The catch-up suggestion removes a step with no Undo

When the run falls behind, tapping “Skip [step] today” removes that step from the current run. Normal Done and Skip actions offer a five-second Undo, but the catch-up action clears the undo state and does not offer a way to restore the step. A mis-tap can leave the user unsure how to return to the original plan.

Recommendation

Offer a short Undo in the same control area after applying the catch-up change. Keep it scoped to this run, as the current action is.

Evidence

ShoesOn/Views/RunView.swift:198-222 applies the action directly. Shared/Services/RoutineStore.swift:284-290 drops the step and clears undo state.

P2, setup continuity

Leaving during the Pro offer restarts setup instead of resuming it

The routine is saved before the notification prompt and Pro offer, while setup is marked complete only after a purchase or “Continue free.” If the app is closed on the offer and reopened, the root view starts onboarding at page one with default draft values. The saved routine is not loaded back into those draft controls, so the user repeats setup and can see a reveal that no longer matches the saved routine.

Recommendation

Persist and restore the onboarding page and answers, or finish the free setup before presenting Pro as a dismissible offer.

Evidence

ShoesOn/App.swift:51-62 selects a fresh onboarding view while setup is incomplete. ShoesOn/Views/OnboardingView.swift:349-380 saves the routine before marking setup complete.

What is working well

Home gives a useful next action

The next start time, leave time, and guess-versus-real gap are visible together.

The run screen explains the tradeoff

It keeps the current step, remaining time, schedule status, and time recovered by a suggested skip together.

Setup demonstrates a personal plan

The reveal turns the user's guesses into a concrete start time before the Pro offer.

Evidence reviewed

Before submission

  • Confirm the launch storefront languages match the languages available in the app.
  • Walk through first launch with notifications denied, then inspect the trial offer and the Home recovery card.
  • Try the catch-up action and verify the user can restore the dropped step.
  • Review onboarding and the active run at the largest accessibility text size and with VoiceOver.
  • Close and reopen the app from the Pro offer, then confirm setup resumes without changing the saved routine.
Scope and limits

Static review of SwiftUI flows, notification and purchase paths, the checked-in App Store and Watch captures above, and existing UI-test coverage. Existing tests cover screenshot flows, common Done and Undo behavior, catch-up, and one-off day changes. They do not cover a denied-notification trial, interrupted setup, large text, VoiceOver progress, or localized screens. No source code was changed and no tests were run. All available simulators were shut down, so this pass does not claim a live runtime check. In particular, the current paywall layout and permission-denied behavior still need a device or simulator review.
